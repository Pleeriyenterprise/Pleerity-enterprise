## 4. Potential Risks

| Risk | Description | Mitigation |
|------|-------------|------------|
| **Layout / responsive** | Changing public header to Midnight Blue + logo can affect alignment, mobile menu, and tap targets. | Keep existing structure; only change background and add/swap logo; test breakpoints. |
| **Theme configuration** | design-tokens.js is wrong; components may import it. Changing it could shift colours in any consumer. | Audit all imports of design-tokens.js; update tokens to guide values; regression-check screens. |
| **Asset loading** | Adding or renaming logo/favicon can 404 if paths or build/public setup are wrong. | Serve from `public/`; use same paths as current references; verify after build. |
| **Cached static assets** | New favicon/logo may be cached by browsers/CDN. | Use cache-busting (e.g. query param or filename version) or appropriate cache headers. |
| **Email rendering** | Inline styles already match guide; changing to external CSS or new structure can break clients. | Keep inline styles; only adjust hex/font if needed. |
| **PDF generation** | Embedding a logo in ReportLab requires image path or URL; server must have access. | Add logo to backend assets or config; use path or URL; handle missing logo gracefully. |
| **Backwards compatibility** | Client branding API (primary_color, secondary_color, logo_url) can override defaults. | Keep current defaults as guide values; ensure tenant branding still overrides where designed. |
| **Tailwind vs design-tokens** | Two sources of “brand” colour (Tailwind + design-tokens.js). | Prefer Tailwind/CSS variables as source of truth; deprecate or align design-tokens.js. |

## 5. Recommended Safe Implementation Plan

### 5.1 Where to store branding assets

- **Recommended:** `frontend/public/` for app-facing assets:
  - `favicon.png` (sizes as needed; match index.html).
  - `pleerity-logo.jpg` (or SVG if preferred; update all `src="/pleerity-logo.jpg"` if name changes).
  - `og-default.png` for social sharing (branded, recommended dimensions e.g. 1200×630).
- **Backend PDFs:** Either (a) a shared static path (e.g. `backend/static/brand/logo.png`) and reference by path in ReportLab, or (b) config (e.g. `BRAND_LOGO_PATH`/URL) so one place controls logo presence and path.

### 5.2 Centralise theme variables

- **Frontend:** Treat `frontend/src/index.css` and `frontend/tailwind.config.js` as the source of truth. Add any missing guide colours (e.g. success #10B981, warning #F59E0B, danger #EF4444, info #3B82F6, neutrals) as CSS variables and/or Tailwind theme extend.
- **design-tokens.js:** Update to use guide hex values (navy #0B1D3A, teal #00B8A9) and align status colours with guide; or deprecate and migrate consumers to Tailwind/CSS variables.
- **Backend:** Keep a single module or config (e.g. `brand.py` or env) defining hex values for emails and PDFs so one change updates all.

### 5.3 Update shared layout components

1. **ClientPortalLayout:** Add logo image in header (same as public/admin: `pleerity-logo.jpg`) next to “Compliance Vault Pro” and tagline; keep existing midnight blue bar.
2. **PublicHeader:** Optionally switch to `bg-midnight-blue` and light text for full alignment with guide; ensure logo and nav remain accessible (contrast, focus).
3. **UnifiedAdminLayout:** No structural change if logo path is correct; ensure logo asset exists and error handling (e.g. onError) keeps layout usable.
4. **PublicFooter:** Already aligned; confirm tagline and link colours match guide.

### 5.4 Update marketing pages

- Use existing PublicLayout/PublicHeader/PublicFooter so that when header/footer get logo and (if desired) Midnight Blue nav, all marketing pages inherit.
- Ensure marketing pages use Tailwind brand classes (`text-midnight-blue`, `bg-electric-teal`, etc.) and avoid hardcoded hex except where necessary.

### 5.5 Update system emails

- Current implementation already matches guide (Inter, #0B1D3A, #00B8A9, #f8fafc). No change required unless adding a logo in email header (then use hosted image URL and alt text).

### 5.6 Update exported documents (PDFs)

1. **Header:** Add “Logo + product name”:
   - In `pdf_report_builder`, `template_renderer`, `compliance_pack`, and any other PDF generators: accept an optional logo path/URL; if present, draw logo image at top, then product name (e.g. “Compliance Vault Pro” or “Pleerity Enterprise Ltd”) using existing brand styles.
2. **Footer:** Standardise footer to: Company name, Website, Support email (plus existing “Generated …” and disclaimers where applicable). Ensure website and support email are in config or constants.

### 5.7 Backwards compatibility

- Keep API branding (primary_color, secondary_color, logo_url, favicon_url) so tenants can override. Defaults in API and in PDF/email code should match guide.
- If design-tokens.js is updated, run a quick audit of imports and test any component that uses it.

### 5.8 Verification before deployment

1. **Visual:** Smoke-test Client portal, Admin, Public (home, key marketing pages), Client and Admin login; confirm logo and favicon load, nav/header/footer colours and contrast.
2. **Responsive:** Check header and logo on small viewports; confirm no overflow or broken layout.
3. **Emails:** Send test emails (welcome, digest, etc.); confirm rendering in at least one client (e.g. Gmail).
4. **PDFs:** Generate at least one of each type (evidence report, compliance pack, order document); confirm logo (if added) and footer (company, website, support) appear and colours match guide.
5. **Build:** Run frontend build and confirm no 404s for favicon or logo in built output.
