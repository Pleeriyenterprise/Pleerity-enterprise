# Pleerity System Architecture

This document describes the high-level architecture of Pleerity as an enterprise Property Compliance OS, with emphasis on how **compliance**, **operations**, **automation**, and **admin oversight** integrate.

---

## 1. Overview

Pleerity is a multi-tenant SaaS platform that provides:

- **Compliance engine:** Requirements, documents, certificates, reminders, compliance scoring, and status (GREEN/AMBER/RED).
- **Operations engine:** Maintenance issues, work orders, contractors, risk signals, invoices, and approvals.
- **Automation:** Scheduled jobs (reminders, compliance recalc, risk signal generation, SLA monitoring, lead nurture, etc.).
- **Admin oversight:** Multi-client visibility, feature flags, risk dashboard, work orders, contractors, audit logs.

The platform is designed so that **compliance and operations are connected**: compliance outcomes can drive risk signals, and risk signals can be turned into actionable issues and work orders with full audit trails.

---

## 2. Compliance engine

- **Properties:** Core entity; each has requirements (e.g. EICR, Gas Safety) and compliance status.
- **Documents / certificates:** Uploaded and evaluated against requirements; expiry and missing items drive reminders and scoring.
- **Compliance scoring:** Per-property and portfolio-level; used for dashboards and reporting.
- **Reminders:** Scheduled and one-off; notify landlords/admins of upcoming or overdue compliance.
- **Outputs:** Compliance status, requirement status, document status, reminder state. These feed into the **risk signal engine** (e.g. overdue requirements → compliance churn risk, EICR → electrical risk).

---

## 3. Operations engine

- **Maintenance issues:** Created by client, admin, or tenant (source=tenant_request). Can be linked to a risk_signal_id when created from a risk signal. Lifecycle: open → triaged → investigating → ready_for_work_order → in_progress → resolved → closed/cancelled. Triage runs on create (severity, SLA, recommended contractor type).
- **Work orders:** Created directly or from an issue. Can be linked to issue_id and risk_signal_id. Assigned to contractors; have status (OPEN, ASSIGNED, IN_PROGRESS, COMPLETED, etc.) and SLA fields.
- **Contractors:** Stored per client/network; assigned to work orders.
- **Invoices:** Created by admin or client, linked to work_order_id, contractor_id, property_id, client_id. Status: pending → approved/rejected/needs_info. Approval workflow and audit are in place.
- **Risk signals:** Generated by scheduled job from property/asset/work order/compliance data. Types include boiler failure risk, damp/moisture, electrical, recurring repairs, maintenance frequency, SLA breach, compliance churn. Signals have recommended_action and can be turned into **issues** or **work orders** via user-confirmed actions (with audit).

---

## 4. Integration: compliance → operations

- **Risk signal generation** uses:
  - Compliance: overdue/missing requirements → compliance churn risk; EICR/electrical data → electrical risk.
  - Operations: work orders, issues, assets (e.g. boiler age, last service) → boiler, damp, recurring repair, SLA breach risks.
- **Flow:**  
  Compliance findings (e.g. EICR expired, requirements overdue) → **risk signals** (with recommended actions) → user chooses **Create issue** or **Create work order** → new issue/work order linked to signal_id → full audit.
- **No blind automation:** Issues and work orders are created only after user confirmation from the risk signal UI (or equivalent), to avoid noise and false positives.

---

## 5. Automation layer

- **Scheduled jobs (e.g. cron/APScheduler):** Daily reminders, compliance recalc, risk signal generation per property/client, SLA monitoring, lead follow-up, digest emails, etc.
- **Risk signal job:** Iterates properties (or client), runs rule set (boiler, damp, electrical, recurring, maintenance frequency, SLA breach, compliance churn), persists active heuristic signals and replaces previous active set for that property.
- **Notification orchestration:** Central send for email/SMS; idempotency, throttling, and logging (message_logs); optional audit events.

---

## 6. Admin oversight

- **Multi-client:** Admin can switch client context; many ops endpoints are scoped by client_id.
- **Feature flags:** MAINTENANCE_WORKFLOWS, PREDICTIVE_MAINTENANCE, CONTRACTOR_NETWORK, INVOICING, etc., gate client and tenant features.
- **Admin risk dashboard:** Aggregates risk signals across clients (or one client). Shows total active, counts by level/type, top properties/clients, recent signals. Filters: client, risk_level, risk_type, status.
- **Ops modules:** Work orders, contractors, (admin) invoice creation, feature controls. Audit logs provide observability for admin and compliance actions.

---

## 7. Data and audit

- **Audit log:** Central audit (e.g. audit_logs collection) with action, actor_id, client_id, resource_type, resource_id, metadata. Covers invoice creation, approval actions, issue/work order creation from risk signals, issue status/closure, tenant issue reporting, and other critical actions.
- **Links between entities:** issue_id on work order; risk_signal_id on issue and work order; work_order_id, contractor_id, property_id, client_id on invoice. These support traceability and reporting.

---

## 8. Security and access

- **Client routes:** Protected by client_route_guard; user has client_id and role (e.g. ROLE_CLIENT, ROLE_CLIENT_ADMIN).
- **Tenant routes:** Tenant can only access assigned properties; report-issue and report-maintenance enforce property assignment.
- **Admin routes:** admin_route_guard; owner/admin for sensitive ops (e.g. feature flags, admin invoice create).

---

This architecture supports the enterprise goal: **compliance and operations are tightly connected**, with clear flows from compliance and asset data → risk signals → user-confirmed issues/work orders → contractors and invoices → approvals and audit, while keeping automation predictable and observable.
